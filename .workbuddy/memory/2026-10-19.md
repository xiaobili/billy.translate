## ALT+SHIFT+D（rich 模式）延迟根因定位

只做诊断，未改插件代码。诊断脚本放在 `.workbuddy/bench/`（sweep.sh / micro.sh / isolate.sh / instrument.sh / instrument2.sh / wlcopy.sh），可复跑。

### 结论：延迟全部在 `bin/pick-text --rich` 抓取阶段，QML/Transport 侧无额外延时

实测（干净 PATH，wtype stub 立即响应，即"应用零延迟"的理想条件）：

| 路径 | 耗时 |
|---|---|
| ALT+D（`--primary` 命中，纯文本） | ~58-70 ms |
| ALT+SHIFT+D（`--rich`，合成 Ctrl+C） | **~875 ms**（min 713 / max 943） |
| ALT+SHIFT+D 失败路径（app 忽略 Ctrl+C） | ~2.1 s 后才报错 |

### 阶段拆解（默认 preCopyDelayMs=350）

| 阶段 | 耗时 | 说明 |
|---|---|---|
| bash 启动 + 3× jq 读配置 | ~20-35 ms | `pick_num` 每个旋钮各起一次 jq，共 3 次 |
| mktemp + mkdir | ~20 ms | |
| 剪贴板备份（list-types + 整份 + N× `--type`） | ~55 ms | N = 剪贴板类型数，实测 5-6 |
| `wl-copy --clear` | ~7-53 ms | 仅 rich 模式 |
| **sleep PRE_COPY_DELAY_MS** | **~364 ms** | 纯等待，等用户松开 Alt/Shift；最大单项 |
| wtype 发 Ctrl+C | ~3-30 ms | |
| poll 首轮 | ~54 ms | `awk` + `sleep 25ms` + 2× `wl-paste`；循环先睡后查，首轮也必付 25ms |
| `read_rich`（list-types + html + python3） | ~155 ms | **python3 冷启动 139 ms** 是大头 |
| **restore（N× `wl-copy --type` + 末尾 `wl-copy`）** | **~155 ms** | 末尾无 `--type` 的 `wl-copy` 单次 ~90 ms |

### 关键发现（可复用知识）

1. **`wl-copy` 无 `--type` 时 ~85-105 ms，带 `--type` 只要 ~13 ms**——前者要同时生成
   text/plain / text/plain;charset=utf-8 / TEXT / STRING / UTF8_STRING 五六种 MIME。
2. **`wl-copy` 每次调用整体替换 offer，不支持一次提供多类型**（实测
   `--type text/html --type text/plain` 只有最后一个生效）。所以 `restore()` 里
   N× `--type` 重放只有最后一次有意义，且随后被无 `--type` 的 `wl-copy` 再次整体覆盖
   → 前 N-1 次是纯浪费，且**用户原有富文本剪贴板被降级成纯文本**（顺带一个正确性问题）。
3. `Overlay.qml:62` `visible: opened && phase !== "picking" && phase !== "idle"`——
   picking 全程不可见（必须让键盘焦点穿透到下层 app），所以这 ~875 ms 是**零反馈黑屏**。
4. `o.bind(keys, desc, cmd, { release = true })` 存在（见
   `/usr/share/omarchy/default/hypr/bindings/voxtype.lua`）。改 release 触发后
   Alt/Shift 多半已松开，`preCopyDelayMs` 可大幅下调——这是降延迟最大的杠杆。

### 坑

- 沙箱 shell 的 PATH 里 WorkBuddy 自带 python3 是坏的（`symbol lookup error`），
  会让 `html-to-markdown` 静默失败、rich 模式退化成输出原始 HTML。
  这是**环境假象**，`/usr/bin/python3` 正常。跑插件相关基准必须用
  `export PATH=/usr/bin:/bin`，否则测出来的数字和行为都是错的。
- bash 工具的 `/tmp` 在命令之间不保留，临时脚本要放工作区内。

## 环境坑（重要，会重复踩）

跑本插件的测试**必须**用干净环境，否则 `python3` 会解析到 WorkBuddy 的坏解释器
（PATH 里 `/home/billy/.workbuddy/binaries/python/versions/3.13.12/bin` 在前），
导致 html-to-markdown 静默失败、rich 模式退化成输出原始 HTML：

```bash
env -i PATH=/usr/bin:/bin HOME=/home/billy USER=billy \
  XDG_RUNTIME_DIR="$XDG_RUNTIME_DIR" WAYLAND_DISPLAY="$WAYLAND_DISPLAY" \
  HYPRLAND_INSTANCE_SIGNATURE="$HYPRLAND_INSTANCE_SIGNATURE" \
  bash tools/test.sh
```

原因：Bash 工具设置了 `BASH_ENV=/opt/WorkBuddy/.../shell-runtime-bash-env.sh`，
**每个** bash 子进程都会 source 它并把 WorkBuddy 路径重新 prepend 到 PATH 最前，
所以在父 shell 里 `export PATH=/usr/bin:/bin` 无效，`env -u BASH_ENV` 也无效，
只有 `env -i` 干净起进程才管用。跑 JS 测试还要把 node 加进 PATH。

## 富文本剪贴板降级修复（v0.5.1，方案 3：自建多 MIME 写入器）

原有 bug：`restore()` 只能靠 `wl-copy` 单类型写回，用户剪贴板被降级成纯文本。
`wl-copy 2.3.0` 的 `-t` 只接受单个 MIME（man 确认），无解 → 自写
`bin/clipboard-write`，用 `zwlr_data_control_v1`（Hyprland 有 v2）。

关键：该协议 `set_selection` **没有 serial 参数**，所以不需要 surface、不需要
输入焦点、不需要合成事件——这是能从脚本里成为 selection owner 的唯一干净路径。
方案对比过的另外两条：GTK4 `GdkContentProviderUnion`（无编译但常驻几十 MB、
启动 200ms+）、C + libwayland（需构建产物）。

### wire 层三个坑（都是实测出来的，不是读文档）

1. **客户端 object id 必须从 2 开始、按请求发送顺序分配**。libwayland 印象里的
   0xFF000000 起点会被 Hyprland 判为 `invalid arguments`。第一条 new_id 必须是
   2，起点 5 也失败；中间有 gap（2,4）反而可以。
2. **`wl_display.sync` 必须发在 `get_registry` 之后**。它是"此前请求"的屏障，
   先发 sync 会让 callback.done 早于 global 事件到达，注册表读成空 ——
   表现为 "no zwlr_data_control_v1 on this compositor"（误导性错误）。
3. 参数分隔符**不能用 `=`**：MIME 类型自带参数 `text/plain;charset=utf-8`，
   会被切成两半。改冒号（RFC 2045 token 不含冒号）。
   诊断靠 LD_PRELOAD 拦 `sendmsg` 抓 wl-copy 真实字节（无 strace，但 gcc/gdb 有）。

### 实现要点

- 数据在 fork 前读进内存：调用方随后 `rm -rf` 备份目录，子进程不能再去读文件。
- fork 后必须 `setsid` + 把 0/1/2 重定向到 /dev/null。否则子进程持有 pick-text
  的 stdout 写端，Quickshell 的 Process 等 EOF 会一直挂着。
- 自动补 `UTF8_STRING`/`STRING`/`TEXT`（指向同一份纯文本）：`wl-copy` 无 `--type`
  时隐式提供这套，XWayland 按名字取，不补就什么都拿不到。
- 空 payload 的 flavour 跳过而非 offer（客户端先选类型后才知道是空的）。
- 退出码 2 = unsupported（无 display / 无协议 / 无内容），pick-text 据此回退。

### 集成与测试

`restore()` 优先 `clipboard-write`（一次调用传全部 `MIME:PATH`），失败或不存在
才走原 `wl-copy` 逻辑。`CLIPBOARD_WRITE` 可覆盖 —— **测试里必须显式设
`/bin/false` 或 stub，否则会 spawn 真实写入器改掉调用者的剪贴板**。

测试 33 → 39（新增 6）；变异验证：完全不用写入器失败 4、提供空 flavour 失败 1、
只交第一个 flavour 失败 1、每 flavour 一次调用失败 1。
端到端对照（真实 wayland + 真实 wl-clipboard，只 stub wtype）：
新路径 pick-text 失败后 `text/html` 仍在；回退路径只剩纯文本 —— bug 复现与修复同时成立。

诊断脚本：`.workbuddy/bench/{wlprobe/probe.c,wlprobe/preload.c,multi-test.sh,
rich-restore-test.sh,mutate-restore.sh,cleanup.sh}`，协议 XML 在
`.workbuddy/bench/protocol/`。

### 新踩的坑

`pkill -f 'bin/clipboard-write'` 会匹配到执行它的 `bash -c` 自身命令行，把自己
杀掉（exit 143）。要 pkill 进程名就把检查写进 .sh 文件再执行，别用内联 bash -c。
